# Agent.md

Правила работы с проектом `hobby-habit-tracker`.

## Цель

Это пользовательский трекер привычек и навыков на React + Vite с Firebase для авторизации и синхронизации. Проект должен оставаться:

- понятным пользователю без технического жаргона в интерфейсе;
- удобным на телефоне и на компьютере;
- пригодным для деплоя на GitHub Pages и Sites;
- безопасным для дальнейших правок без ломки существующих сценариев.

## Архитектурные правила

- `src/App.tsx` держать как оркестратор состояния, эффектов и обработчиков верхнего уровня.
- Визуальные блоки выносить в `src/components/`.
- Чистые функции, константы, форматтеры и UI-нейтральные типы выносить в `src/lib/`.
- Firebase-логику, localStorage и облачную синхронизацию держать в `src/storage.ts`, не размазывать по компонентам.
- Новую фичу сначала пытаться встроить в существующую структуру, а не добавлять ещё один монолитный файл.

## UI и UX

- Десктоп и мобильный сценарии считать разными интерфейсами, а не просто ужатой одной таблицей.
- На мобильном первым экраном должен быть основной рабочий контент, а не вторичная статистика.
- Поповеры и модалки обязаны закрываться по клику вне области и по `Escape`, если это уместно.
- Не добавлять в интерфейс странные текстовые псевдо-тумблеры и спорные контролы без проверки визуально.
- Перед финалом проверять, не появился ли горизонтальный скролл там, где он ломает соседние блоки.
- Если у проекта уже есть принятые иконки и названия, не подменять их “на своё усмотрение” без явной просьбы.

## Бренд и ассеты

- Рабочее название текущего продукта: `Hab-Hob`.
- Если пользователь отдельно не просил переименование, не менять название в интерфейсе, метатегах, превью и ассетах.
- Использовать утверждённый логотип как единый источник для:
  - шапки приложения;
  - favicon;
  - превью ссылки;
  - web manifest и related icons.
- Не подменять утверждённый логотип временными заглушками, галочками, случайными пиктограммами или “быстрыми” иконками.
- При изменении логотипа или favicon проверять, как это выглядит:
  - во вкладке браузера;
  - в шапке приложения;
  - в превью ссылки в мессенджерах;
  - на GitHub Pages и Sites.
- Если есть несколько версий логотипа, перед внедрением явно уточнять, какая из них считается основной.
- Для новых брендовых файлов придерживаться понятных имён, например `brand-mark`, `favicon`, `og-image`, без хаотичных дублей.

## Данные и поведение

- Сохранять совместимость со структурой `TrackerState`.
- Любое новое пользовательское состояние, которое влияет на UX между сессиями, сохранять в `preferences`, если это логически настройка интерфейса.
- Для заметок дня, раскрытия проектов и похожих вещей продумывать не только UI, но и постоянное хранение состояния.
- При удалении проекта учитывать связанные дочерние элементы и их записи.
- При изменении схемы состояния добавлять безопасную нормализацию в `loadLocalState` / `normalizeState`.

## Firebase и auth

- Не хранить пароли самостоятельно и не логировать чувствительные данные.
- Использовать только возможности Firebase Auth, не изобретать собственную авторизацию.
- Ошибки входа переводить в человеческие сообщения.
- Любые изменения auth-потока проверять и для обычного браузера, и для мобильных встроенных браузеров, где popup может ломаться и нужен redirect fallback.
- Если авторизация не работает на новом домене, первым делом проверять `Authorized domains` в Firebase.

## Визуальная проверка

- После заметных UI-правок обязательно запускать локальную проверку в браузере.
- Не считать задачу законченной только потому, что TypeScript собрался.
- Проверять минимум:
  - десктоп;
  - мобильную вёрстку;
  - светлую и тёмную темы;
  - поповеры, модалки, раскрытие проектов;
  - auth-блок, если он затронут.

## Обязательная проверка перед завершением

После каждой существенной правки обязательно выполнить:

```bash
npm run build
npm run lint
```

Если изменялся UI, дополнительно проверить локально в браузере.

## Деплой

- Не пушить и не деплоить автоматически, если пользователь прямо не попросил.
- Если пользователь пишет “запушь”, это означает ожидание обновления GitHub Pages и Sites, а не только локального коммита.
- Перед деплоем убедиться, что версия в интерфейсе обновлена, если менялось заметное пользовательское поведение.
- Для этого репозитория GitHub Pages публикуется из ветки `gh-pages`, а не из `main`.
- Не смешивать два способа публикации GitHub Pages одновременно.
- `gh-pages` считать артефактной веткой: в ней не ведётся обычная разработка, туда попадает только содержимое `dist/`.
- Для GitHub Pages использовать один явный путь публикации: `npm run deploy:pages`.
- Sites публиковать отдельно от GitHub Pages; успешный деплой Sites не означает, что GitHub Pages уже обновился.

## Git workflow

- `main` — продуктовая стабильная ветка исходников.
- `dev` — ветка интеграции для накопления проверенных изменений.
- `feature/*` — короткие ветки под отдельные задачи.
- `gh-pages` — только опубликованная статическая версия сайта.
- Если задача связана только с публикацией Pages, не тащить в неё новые функциональные изменения.
- Перед публикацией в `gh-pages` сначала проверять локальную сборку, потом публиковать артефакт.
- Если пользователь просит “запушить”, нужно явно понимать:
  - исходники в `main`/`dev`;
  - GitHub Pages в `gh-pages`;
  - Sites отдельным деплоем.

## Коммиты и версии

- Каждый коммит должен иметь один понятный смысл. Не смешивать в одном коммите UI, auth, деплой и бренд, если это можно разделить.
- Перед коммитом коротко формулировать пользователю:
  - в какую ветку идёт коммит;
  - как будет называться коммит;
  - что именно в него входит.
- Для сообщений коммитов использовать понятный формат:
  - `feat(tracker): add day notes`
  - `fix(firebase): normalize legacy cloud state`
  - `fix(pages): publish stable build to gh-pages`
  - `chore(repo): standardize branching workflow`
- Если изменение пользовательски заметное, перед деплоем обновлять версию в `package.json` и в интерфейсе.
- Версии вести по простому semver-подобному правилу:
  - `patch` (`1.7.4` -> `1.7.5`) — мелкие исправления и небольшие UX-правки;
  - `minor` (`1.7.4` -> `1.8.0`) — новые функции без ломки существующего поведения;
  - `major` (`1.x.x` -> `2.0.0`) — редкие крупные несовместимые изменения.
- Для каждой версии обновлять `CHANGELOG.md`.
- Если менялась только внутренняя организация репозитория, версию продукта не поднимать.

## Обязательный старт новой сессии

Перед любыми правками, особенно после смены модели или длинной паузы, сначала обязательно:

1. Проверить текущую ветку и `git status`.
2. Проверить существующие ветки: `main`, `dev`, `gh-pages`, `feature/*`.
3. Проверить, откуда реально публикуется GitHub Pages.
4. Прочитать `Agent.md` и не придумывать процесс заново.
5. Не пушить ничего, пока не стало ясно:
   - что меняется в исходниках;
   - что меняется в публикации;
   - нужна ли отдельная публикация на Sites.

## Правило против поломки деплоя

- Не смешивать в одном этапе разработку фичи и починку публикации.
- Если GitHub Pages сломан, сначала чинить только публикационный контур, без новых продуктовых изменений.
- Если `main` обновлён, это ещё не означает, что GitHub Pages уже обновился.
- Перед выводом “всё запушено” обязательно отдельно проверить:
  - `main`;
  - `gh-pages`;
  - живой URL GitHub Pages;
  - живой URL Sites, если он затронут.

## Стиль изменений

- Делать точечные и объяснимые изменения.
- Не устраивать лишних переименований без причины.
- Не ломать пользовательские данные в localStorage и Firestore.
- Если можно выбрать между быстрым костылём и чистым расширением текущей архитектуры, выбирать второе.
